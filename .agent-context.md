# Bot Crossing Hive — working notes

**What this repo is.** A fork of `bot-crossing` (this file's own history below is inherited from
it, forked on 2026-09-18 with full uncommitted working-tree state at fork time — not just its last
commit). Bot Crossing itself is single-machine, single-user: one person, one local server that
scans that same machine's own Claude Code/Codex session files. This fork's whole reason to exist
is the piece that breaks: a team, all working on one shared project, whose agent sessions each
live on their own separate machine. Year-long senior project — this is meant to be built for real,
not a weekend hack.

**The design, as scoped in conversation (2026-09-18) before any of it was built:**
- **One shared city per project, not per-directory districts.** Splitting a repo into "districts"
  (top-level folders, say) was considered and dropped — it adds a real design problem (how do you
  define a district that means anything for an arbitrary repo layout?) for a benefit multiple
  buildings-per-city already gives for free. One city, one project, matches how a team actually
  works (realistically one project at a time).
- **A building = one completed agent thread**, same unit `bot-crossing` already uses on a single
  machine — nothing new to invent there, just aggregated across everyone's machines instead of one.
- **Building size = lines of code, not transcript bytes.** `bot-crossing` sizes a building off
  `sizeBytes` (raw transcript size) today — a chat-length signal, not a "how much did this session
  actually build" signal. Plan: count lines out of `Edit`/`Write`/`MultiEdit` tool-call inputs
  already sitting in that session's own transcript (the harness adapters already parse tool calls
  for other things — `transcriptSkillCounts` in `server/api.mjs` is the existing pattern to mirror)
  rather than shelling out to `git diff` per thread. Known tradeoff, accepted deliberately: this
  double-counts a line edited three times before landing, and still counts a line later reverted —
  approximate, not exact-to-the-final-commit. Mapping a thread to the commit(s) it actually produced
  (for an exact diff-based count instead) was considered and explicitly deferred, not solved.
- **Cumulative, not live.** A city only ever grows — it's a scoreboard of everything the team has
  ever shipped over the project's life, not a live "how busy is everyone right now" pulse. This
  was an explicit choice over a live-concurrency model (buildings would then need to shrink/settle
  as agents finish, which was considered and rejected in favor of the permanent-monument framing).
- **Never track who, how much, or when someone's live.** Explicit non-goal, stated directly: this
  is not a productivity-monitoring tool. The shared store does need an internal id per push
  (`device_id` or similar) for dedup/rate-limiting/debugging, but it is never surfaced anywhere in
  the UI — the only thing ever rendered is aggregate counts. If a feature ever needs to show a
  per-person breakdown, that is a deliberate reversal of this decision and should not happen by
  accident (e.g. by piping `device_id` straight into a label somewhere).
- **Dedup is free, via thread ids.** Every thread id (`claude-code:<uuid>`, `codex:<uuid>`) is
  already globally unique across every machine and every harness (see the id-prefixing rule in
  `server/harnesses/README.md`, inherited from upstream). So the shared store can just be a table
  of "completed threads ever seen," upserted keyed by thread id — inserting the same id twice is a
  no-op. That also means a local instance never needs to track "have I already reported this
  thread" itself: it can resend everything it knows on every sync and let the upsert dedupe it.
- **What syncs, what never does.** Push candidates: thread id, a repo-*relative* path (never
  absolute — `C:\Users\alice\...` vs `C:\Users\bob\...` would never match across machines), a
  lines-of-code size, a completed-at timestamp, the internal device id. Never synced: prompts,
  titles, or any transcript content — those stay on the machine that made them. Not yet decided:
  whether the relative-path field ends up used for anything, now that districts were dropped —
  probably still worth keeping (future features, or just debugging), just not used to split a
  project into multiple cities.
- **Backend: Supabase (Postgres), not Firebase.** Chosen over Firebase specifically because
  "sum of lines of code per project, cumulative" is a `GROUP BY`/`SUM` query away in SQL, and a
  year-long project will likely want to query this data in shapes not anticipated yet (a
  history-over-time chart, say) — Postgres handles that more gracefully than a NoSQL aggregate.
  Considered and rejected: using a Claude-side Artifact's own database capability as the shared
  store — it isn't reachable as a plain HTTP API from an arbitrary local server, only from inside
  a published Artifact page or through Claude's own tool calls, so it can't be what many
  independent local `bot-crossing-hive` servers push to directly.
- **Sync cadence: slow poll, not live.** Each local server pushes/pulls on a cadence of minutes,
  not a live subscription — consistent with "cumulative, not live" above, and much simpler to get
  right than a real-time sync layer for a gain (instant cross-machine updates) that doesn't
  actually matter here.

**Not yet decided — still open when this file was written:**
- How a local instance authenticates to Supabase to push/pull (a shared team secret is the simplest
  option; real per-person auth is more setup for a benefit — knowing *who* pushed what — that the
  "never surfaced" identity rule mostly makes moot, so the shared-secret route seems more likely to
  win, but wasn't actually decided).
- None of the above is implemented yet — no Supabase project exists, no sync client code, no
  district-free city-rendering changes, no lines-of-code transcript parser. This file is the
  design record from before any of that was built; if you're reading this well after 2026-09-18,
  check whether it's already done before re-deriving it.

# Bot Crossing — working notes

Fork of the upstream repo, running locally on Windows. Diverges from upstream in a few places
that aren't in any PR yet:

- **Windows terminal-opening support** (`server/lib/win.mjs`, new file): the `claude://` /
  `codex://` deep links have no real handler on this machine (a broken/stale registry entry for
  `claude://`, nothing at all for `codex://`), so `openThread`/`newSession` fall back to a real
  terminal command. Tries Wave Terminal (`wsh run`) first, then Windows Terminal, then a bare
  console window. Already-open threads get focused (`wsh focusblock`) via a block tagged with
  `bot-crossing:thread=<id>` in `setmeta`, instead of duplicating.

  **`wsh` needs env vars this server can't get on its own, and one real bug this repo had.**
  Bot-crossing's server is an external process from Wave Terminal's point of view — not a block
  it spawned itself — so unlike an interactive Wave terminal, it never gets these injected:
  - `WAVETERM_JWT` — every `wsh` command but the hidden `token` one refuses to run without it.
    Get a fresh one from any real Wave Terminal block: `echo $env:WAVETERM_JWT` (PowerShell) /
    `echo $WAVETERM_JWT` (bash). Long-lived (the current one expires 2027) — it does **not**
    need to come from the *same* block that's still open, a signed bearer token from any block
    works. Baked into the Startup-folder launcher (`bot-crossing.vbs`) — see its own comments if
    this ever needs redoing.
  - `WAVETERM_TABID` — `wsh run` needs this to know which tab a new block belongs in; without it,
    block *creation* fails outright (`blocks list`/`focusblock` still work with just the JWT,
    which is a misleading half-working state — it looks like dedup works because nothing new
    ever gets created to prove otherwise). Same source: `echo $env:WAVETERM_TABID`. Also baked
    into the launcher.
  - **The actual code bug**, independent of either env var: `wsh -b <id>` needs a full ORef
    (`block:<uuid>`), not the bare id `wsh blocks list` hands back in its JSON. A bare id is only
    resolved via a `WAVETERM_BLOCKID`-relative RPC lookup that nothing here has any reason to
    set, so `focusblock`/`setmeta` failed with `no WAVETERM_BLOCKID env var set` even with a
    valid JWT+TABID — silently, since the failure was caught and swallowed, so blocks kept
    getting created untagged, which meant dedup could never find them next time either. Fixed in
    `win.mjs` by prefixing every `-b` argument with `block:`. Traced by reading
    `resolveSimpleId`/`isFullORef` in `wavetermdev/waveterm`'s own `cmd/wsh/cmd/wshcmd-root.go` —
    if `wsh` ever mysteriously stops tagging/focusing again, that source is the place to recheck
    first, not the JWT/TABID (which have their own distinct, differently-worded error messages).
- **Exact Wave Terminal placement** — the web view block gets its own column, new terminal
  blocks fill columns capped at 2 stacked each. Stock `wsh run` has no placement flags even
  though the RPC (`CommandCreateBlockData.TargetBlockId`/`TargetAction`) supports it, so
  `tools/bin/wsh-patched.exe` is a locally-built `wsh` with `--target`/`--split` added — see
  `tools/README.md` to rebuild it (gitignored, not checked in) and `tools/wsh-run-target-split.patch`
  for the actual diff. `win.mjs` falls back to plain `wsh.exe` on PATH if the patched copy is
  missing. New columns must always anchor-split off the web block specifically, never off a
  previous column's own blocks — Wave's tree algorithm only inserts a sibling when the target's
  *parent* is already a row, and a 2-stacked column's blocks are children of a column-group node
  instead, so splitting relative to them nests inside that group rather than beside it.
- **Codex adapter** (`server/harnesses/codex.mjs`) now resolves the `codex` CLI the same way
  Claude Code's adapter does, for the same reason.
- **New conversation** now asks which harness (Claude Code vs Codex) when more than one is
  detected — a small dropdown, not a modal (`src/ui/hud.js` `pickHarness`).
- **"Open in VS Code" button** per repo zone (`/api/open-editor` in `server/api.mjs`) — spawns
  `code` via `cmd.exe /c` rather than directly, since Node refuses to spawn `.cmd` files
  directly (CVE-2024-27980) and this crashed the server once already.
- **Convert-to-markdown upload** — a global toolbar button (`#btn-convert`/`#file-convert` in
  `src/ui/hud.js`) picks a PDF/doc/image, POSTs it as base64 JSON to `/api/convert-to-markdown`,
  and copies the result to the clipboard (`convertToMarkdown` action in `src/main.js`) so it can
  be pasted straight into a Claude Code/Codex prompt. Server side (`server/api.mjs`) writes the
  upload to a temp file and shells out to `python -m markitdown <file>` (Microsoft's
  [markitdown](https://github.com/microsoft/markitdown) — a **Python** package, `pip install
  "markitdown[all]"`, already installed on this machine; `-m` avoids depending on pip's Scripts
  dir being on PATH, mirroring how `editorCli` resolves `code`). Base64-in-JSON rather than
  multipart, capped at 30MB of request body (~22MB raw file after base64 overhead) — deliberately
  no multipart parser for one upload. Deliberately NOT written into `.agent-context.md` or any
  project file — clipboard-only was the explicit choice, to avoid this file (or a repo) silently
  growing every converted PDF's full text.
  - Also reachable by pasting (Ctrl+V) or dragging a file anywhere on the page — same
    `actions.convertToMarkdown`, wired in `main.js` next to the keydown handler. Paste only acts
    when the clipboard actually holds a file/image (`item.kind === 'file'`), so plain text paste
    into the context editor or anywhere else is untouched. Drag-and-drop tracks enter/leave depth
    rather than toggling on every `dragleave`, since entering a child element fires its own
    `dragenter` before the parent's `dragleave` and a naive toggle flickers the `.drag-active`
    overlay (`styles.css`) while dragging across the sidebar/canvas boundary.
  - **Images never go through `markitdown` at all — confirmed empty stdout on this machine**,
    even for a PNG with rendered text baked in (no OCR). Its only image-to-text paths are Azure
    Document Intelligence (`-d`/`-e`) or Azure Content Understanding (`--use-cu`), both paid
    cloud endpoints with no local/offline fallback in the CLI. So `convertToMarkdown` in
    `main.js` branches on `file.type.startsWith('image/')` before ever calling the server —
    an image goes to `actions.copyImage` instead, which puts the actual image bytes on the
    clipboard as `image/png` (via `toPngBlob`, since Chromium's Clipboard API only accepts
    `image/png` in a `ClipboardItem` — anything else is silently rejected, so a JPEG/WebP is
    redrawn onto a canvas first) rather than routing it through text conversion for nothing.
    Claude Code reads pasted images natively, so this is strictly better for images than
    markdown ever was.
  - **Pasting that clipboard image into the Claude Code CLI itself needs `Alt+V` on Windows, not
    `Ctrl+V`** — confirmed against Claude Code's own docs. Windows terminals (Wave Terminal
    included) commonly intercept `Ctrl+V` before Claude Code's own paste handler ever sees it,
    so `Ctrl+V` there does nothing rather than inserting an `[Image #N]` chip; `Alt+V` is Claude
    Code's own Windows-specific shortcut for exactly this. macOS/Linux stay `Ctrl+V`/`Cmd+V`. The
    `copyImage` toast in `main.js` says this outright so it isn't rediscovered per session.
    Referencing the file by path in the prompt (`Analyze this image: C:\path\to\file.png`) or
    drag-and-drop onto the Claude Code window both work as a terminal-agnostic fallback.
- **Skills + context visible in the sidebar, with real create/edit/save on the context side** —
  `/api/skills` (scans `.claude/skills/` and `.agents/skills/`, project + user level, for
  directories with a `SKILL.md`) and `/api/context` (this file — `GET` to read, `PUT` to write,
  in `server/context.mjs`) feed two sections in the repo sidebar. `server/api.mjs` has a small
  hand-rolled YAML-frontmatter reader for `name`/`description` — not a general parser, just
  enough for SKILL.md's folded-scalar descriptions.
  - `listDirs` in `server/lib/fsutil.mjs` follows symlinks/junctions now — it didn't originally,
    which silently dropped every skill `sync-skills.mjs` had bridged in (a raw `Dirent` from
    `readdir` reports a junction as neither file nor directory; only a `stat` through it says
    what it actually is). If a linked skill ever goes missing from the sidebar again, that
    function is the first thing to check.
  - `server/context.mjs` does revision-checked, atomic writes (temp file + rename, sha256 content
    hash as the revision) so two tabs — or an edit here racing a `Stop`-hook nudge finishing
    elsewhere — can't clobber each other; a mismatched revision comes back as 409 with the
    caller's draft left untouched. `loadProjectExtras` in `main.js` re-fetches skills/context on
    a cooldown (`POLL_MS`, same as thread polling) rather than once per project selection, and a
    failed fetch doesn't start that cooldown — so it's not just a create-once snapshot, and a
    failure retries on the very next poll instead of needing the project reselected.
  - Note: this exact module got rebuilt once already — an earlier version of it existed for a bit
    during a different agent's concurrent work on this file, then disappeared (the import and the
    file both), apparently reverted as part of their own edits. If a second `context.mjs` shows up
    from elsewhere, reconcile rather than assume either one is stale.
  - Each skill also carries a `uses` count now — how many times it's actually fired, not just
    whether it's installed. Claude Code only: a skill invocation is a `tool_use` content block
    with `name: "Skill"` and `input.skill` giving which one (confirmed against real local
    transcripts). `scanSkillUsage`/`transcriptSkillCounts` in `server/api.mjs` scan a project's
    own `~/.claude/projects/<encoded-cwd>/*.jsonl`, mtime-cached per file the same way
    `claude-code.mjs`'s own `transcriptMeta` is. Codex has no equivalent yet — traced its skill
    system to `codex-rs/ext/skills/` (a `skills.read`/`skills.list` tool pair) but every local
    Codex session ever checked (10+, including sessions with skills available) has never actually
    invoked one, so the exact wire-format tool name a real invocation would use is still
    unconfirmed. Needs a real example to check against before it can be added.
  - "Browse skills" installs from a real registry — Claude Code's own plugin marketplace system.
    Every marketplace `extraKnownMarketplaces` (in `~/.claude/settings.json`) names, plus the
    built-in `claude-plugins-official`, gets cloned locally under
    `~/.claude/plugins/marketplaces/<name>/.claude-plugin/marketplace.json` the moment it's
    known — a real, `$schema`-documented format (`plugins[].skills[]`, paths relative to each
    plugin's own `source`). `listRegistrySkills`/`installRegistrySkill` in `server/api.mjs`
    flatten that into a browsable list (22 real skills found across the user's 3 community
    marketplaces) and copy — never symlink — an installed one into the project's own
    `.claude/skills/<name>`; `sync-skills.mjs` bridges it to `.agents/skills` on the next
    session, same as any hand-written skill. The official marketplace mixes in plugins sourced
    from an external repo (`{"source": "git-subdir", "url": "..."}` instead of a local relative
    path) — those are skipped, not fetched, since nothing here has cloned them; only community
    marketplaces with local paths are currently browsable this way.
  - **Adding a marketplace nobody's configured yet** — a name, URL, or `owner/repo` the user found
    and typed in, not just the ones already in `extraKnownMarketplaces` when the server started.
    The registry modal has an "Add" input (`.registry-add` in `hud.js`) wired to
    `addMarketplace(source)` in `server/api.mjs`, which shells out to Claude Code's own
    non-interactive command — `claude plugin marketplace add <source> --scope user` (confirmed via
    `claude plugin marketplace add --help`) — rather than reimplementing its git-clone-plus-
    `extraKnownMarketplaces`-bookkeeping. `--scope user` means it also registers for real Claude
    Code sessions, not just this registry. `claude.cmd` is an npm shim on this machine (no
    `claude.exe`), so it's invoked through `cmd.exe /c` the same way `openEditor` wraps `code.cmd`.
    Once the CLI clones it, `listRegistrySkills` already picks it up on its very next scan — no
    other change needed. Live-tested (validation paths, and a real invocation against a
    deliberately-invalid path to confirm the CLI actually runs and its error surfaces correctly)
    without actually adding a marketplace to the user's real config, since that's a persistent
    change outside the scope of a code-review test.
  - **Real bug, found and fixed 2026-09-17: `listRegistrySkills` only read a plugin's *declared*
    `skills[]` field in marketplace.json — but that field is optional, and plenty of real plugins
    ship a skill without ever listing it there.** Caught because the user asked why "ponytail"
    (already confirmed working as a plugin) never showed up in the registry: its marketplace.json
    has no `skills` field at all, yet the plugin genuinely ships six — `ponytail`, `ponytail-audit`,
    `ponytail-debt`, `ponytail-gain`, `ponytail-help`, `ponytail-review` — at the conventional
    `<plugin-source>/skills/<name>/SKILL.md` layout (also a duplicate copy under `.openclaw/skills/`
    for a different harness, correctly not picked up since only the plugin's own declared `source`
    is scanned). Same story for "impeccable" (1 undeclared skill). Fixed by having
    `listRegistrySkills` also `listDirs` each plugin's own `<source>/skills/` folder directly —
    **but only when that plugin's own `skills[]` is empty**, not as an always-on supplement. The
    first version of this fix scanned unconditionally and broke on marketplaces where several
    plugins share one `source` root (every callstack plugin points at `./`): each plugin's
    convention-scan found *everyone's* skills under that shared folder, not just its own — a
    26-way cross-product with wrong `plugin` attribution, caught live before it shipped by
    checking one marketplace's entries for duplicates on a hunch. Final count: 58 real skills
    across the same four already-configured marketplaces, no duplicates, spot-checked clean.
  - **Registry modal: grouped by marketplace, plus a search box.** 58 skills as one flat
    alphabetical list made an entry like "evaluation" meaningless without hunting for a small
    label. `_renderRegistry` in `hud.js` now groups rows under a `.registry-group-title` heading
    per marketplace; each row's own small label switched from marketplace (redundant once it's the
    section heading) to plugin, more useful within a marketplace that ships several plugins. A
    separate `#input-skill-search` box (deliberately distinct from the "Add marketplace" input, so
    the two can't be confused) filters name/marketplace/plugin/description as you type, client-side
    against a cached copy (`_registrySkills`) — no refetch per keystroke. `_setRegistrySkills` is
    the one place both the initial load and a fresh add/install response funnel through, so an
    in-progress search survives either without being silently cleared.
  - **Browse also lists locally-authored skills now, not just marketplace ones.** User pushed on
    this directly after the "eli5 isn't in Browse" explanation — a fair point: "browse what skills
    exist" reasonably means all of them, not just the ones a marketplace happens to know about.
    `_setRegistrySkills` folds in anything from the sidebar's own last `setSkills` fetch
    (`_installedSkillsFull`, added for this) whose name isn't already in the registry scan, tagged
    `marketplace: 'On this machine'` so it gets its own group. Already-installed either way, so the
    existing `installed.has(...)` check needed no changes to mark it "Installed" correctly. `eli5`
    itself confirmed real (scope `user`, well-formed frontmatter) via a direct `/api/skills` check
    before shipping this, not just trusted on the user's say-so.
  - **Groups are collapsible, collapsed by default.** `_openRegistryGroups` (a `Set` of expanded
    marketplace names, empty until clicked) drives it — each heading is a real `<button>` with a
    caret and `aria-expanded`, toggled by `_toggleRegistryGroup`. A search in progress
    force-expands every group regardless of that state (`forceExpanded` in `_renderRegistry`) so a
    match sitting inside a collapsed one isn't invisible; clearing the search reverts to whatever
    was actually toggled open. (Note: the "grouped under one category" bug report that led here
    turned out to not be a logic bug — server data and the built bundle were both already correct,
    five distinct marketplaces — it was the browser running a stale cached copy of the JS from
    before grouping was added; the JS bundle is served `immutable, max-age=1y` by design for its
    hashed filename, so a tab that hasn't done a real reload since won't see a new one. Worth
    ruling out first if a "the UI isn't doing X" report ever contradicts what the served bundle and
    a direct `curl` of the API actually show.)
  - **Skills can be deleted, not just installed — and delete is a move to `.trash`, not a real
    delete.** A "×" on each sidebar skill row (`.skill-delete` in `hud.js`, visible on row hover)
    calls `deleteSkill(name, scope)` → `POST /api/skills/uninstall` → `uninstallSkill` in
    `server/api.mjs`, which `fsp.rename`s the folder into a `.trash` subfolder of wherever it
    actually lived (`<root>/.trash/<name>`) instead of `fsp.rm`-ing it. Caught live: a
    marketplace-installed skill can always be put back by installing it again, but a hand-authored
    one (no marketplace behind it at all — the user pointed at their own "eli5" skill as the
    example) would have had no way back at all under a real delete. `scanSkillDir`'s one-level-deep
    walk means a trashed skill's `SKILL.md`, one directory deeper now, never resurfaces in the
    normal scan on its own. A "Removed (N)" section appears under the skill list only when there's
    something to restore, each row with its own **Restore** button
    (`restoreSkill(name, scope)` → `POST /api/skills/restore`) that renames it straight back.
    `scanSkillDir` carries `dir` (absolute folder) and `scope` (`'project'`/`'user'`) per entry
    internally; the GET `/api/skills` route strips `dir` before responding (no reason to ship an
    absolute path — both uninstall and restore re-derive it server-side from a fresh scan rather
    than trusting one sent back, same reasoning `installRegistrySkill` uses, more important here
    since these still move real files) and now also returns a `trashed` array alongside `skills`
    (via the new `scanTrashedSkills`). A user-level skill's confirm-dialog wording is stronger
    ("removes it for every project") since deleting one there affects every project, not just the
    open one — restoring is scoped the same way. Re-trashing a same-named skill overwrites its own
    last trashed copy rather than erroring (one generation of undo, not a full history — the useful
    case, not the general one). Live-tested the full loop end-to-end (install → uninstall →
    confirmed moved into `.trash` on disk and in the `trashed` list, not `skills` → restore →
    confirmed back in `skills`, gone from `trashed`) with a throwaway `skill-creator` copy,
    including final real cleanup (uninstalled again, then the `.trash` copy actually deleted too).
- The production build (`npm run build` → `dist/`) is served by a hidden launcher in the
  Windows Startup folder (`node server/serve.mjs`), so `localhost:5274` is always up. Editing
  frontend source needs a rebuild (`npm run build`) to show there; editing `server/*.mjs` needs
  the server process restarted (it imports them once at startup, no bundling, no hot-reload).
  `npm run dev` is separate and needs the port free.

**Shared skills across harnesses**: Claude Code and Codex use the same open SKILL.md format but
scan different folders (`.claude/skills/` vs `.agents/skills/`). `~/.claude/hooks/sync-skills.mjs`
runs as a SessionStart hook in both tools' configs, symlinking (Windows junction) any real skill
directory (has `SKILL.md` at its root) that's missing from the other side. Deliberately does not
blanket-symlink the whole `.claude/skills` folder — it also holds Claude Code's own internal
skill-cache bookkeeping, which has no business in Codex's directory.

**This file gets a nudge to stay current**: `~/.claude/hooks/context-reminder.mjs` runs as a
`Stop` hook in both tools — blocks a turn from ending and asks whether anything from the session
is worth adding here. Periodic, not one-shot: at most once per 30 minutes per session (a marker
file's mtime is the cooldown), so a long session gets reminded more than once instead of only
near the very start. **Global, not scoped to this repo** — same hook fires in every git repo the
user works in with Claude Code/Codex, and it now auto-creates a bare-title `.agent-context.md`
the first time it would've reminded a session in a repo that doesn't have one yet (used to stay
silent forever in that case, requiring a human or an agent to bootstrap it by hand — changed
2026-09-18 after the user noticed a heavily-used sibling repo, firefly, still had no context file
despite lots of Claude Code time in it). Only git repos qualify (`git rev-parse` must succeed) —
never fires in a non-repo working directory.
