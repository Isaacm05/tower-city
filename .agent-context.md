# Bot Crossing Hive — working notes

**What this repo is.** A fork of `bot-crossing` (this file's own history below is inherited from
it, forked on 2026-09-18 with full uncommitted working-tree state at fork time — not just its last
commit). Bot Crossing itself is single-machine, single-user: one person, one local server that
scans that same machine's own Claude Code/Codex session files. This fork's whole reason to exist
is the piece that breaks: a team, all working on one shared project, whose agent sessions each
live on their own separate machine. Year-long senior project — this is meant to be built for real,
not a weekend hack.

**The design, as scoped in conversation (2026-09-18) before any of it was built:**
- **One shared city per project, not per-directory districts.** Splitting a repo into "districts"
  (top-level folders, say) was considered and dropped — it adds a real design problem (how do you
  define a district that means anything for an arbitrary repo layout?) for a benefit multiple
  buildings-per-city already gives for free. One city, one project, matches how a team actually
  works (realistically one project at a time).
- **A building = one completed agent thread** — **superseded 2026-09-21, see below.** Building
  one per thread was the original plan and shipped first, but reversed the same day once real
  usage showed 100+ threads (real + simulated) crowding two plots: the user's call was that a
  plot's building should grow with *how much code the project has*, not with *how many agent
  sessions touched it*. Threads still each drive their own astronaut — only the building count
  changed. Left this bullet in place, struck through in spirit, so the "why" of the reversal
  isn't lost; the current model is fully described further down.
- **Building size = lines of code, not transcript bytes.** `bot-crossing` sizes a building off
  `sizeBytes` (raw transcript size) today — a chat-length signal, not a "how much did this session
  actually build" signal. Plan: count lines out of `Edit`/`Write`/`MultiEdit` tool-call inputs
  already sitting in that session's own transcript (the harness adapters already parse tool calls
  for other things — `transcriptSkillCounts` in `server/api.mjs` is the existing pattern to mirror)
  rather than shelling out to `git diff` per thread. Known tradeoff, accepted deliberately: this
  double-counts a line edited three times before landing, and still counts a line later reverted —
  approximate, not exact-to-the-final-commit. Mapping a thread to the commit(s) it actually produced
  (for an exact diff-based count instead) was considered and explicitly deferred, not solved.
- **Cumulative, not live.** A city only ever grows — it's a scoreboard of everything the team has
  ever shipped over the project's life, not a live "how busy is everyone right now" pulse. This
  was an explicit choice over a live-concurrency model (buildings would then need to shrink/settle
  as agents finish, which was considered and rejected in favor of the permanent-monument framing).
- **Never track who, how much, or when someone's live.** Explicit non-goal, stated directly: this
  is not a productivity-monitoring tool. The shared store does need an internal id per push
  (`device_id` or similar) for dedup/rate-limiting/debugging, but it is never surfaced anywhere in
  the UI — the only thing ever rendered is aggregate counts. If a feature ever needs to show a
  per-person breakdown, that is a deliberate reversal of this decision and should not happen by
  accident (e.g. by piping `device_id` straight into a label somewhere).
- **Dedup is free, via thread ids.** Every thread id (`claude-code:<uuid>`, `codex:<uuid>`) is
  already globally unique across every machine and every harness (see the id-prefixing rule in
  `server/harnesses/README.md`, inherited from upstream). So the shared store can just be a table
  of "completed threads ever seen," upserted keyed by thread id — inserting the same id twice is a
  no-op. That also means a local instance never needs to track "have I already reported this
  thread" itself: it can resend everything it knows on every sync and let the upsert dedupe it.
- **What syncs, what never does.** Push candidates: thread id, a repo-*relative* path (never
  absolute — `C:\Users\alice\...` vs `C:\Users\bob\...` would never match across machines), a
  lines-of-code size, a completed-at timestamp, the internal device id. Never synced: prompts,
  titles, or any transcript content — those stay on the machine that made them. Not yet decided:
  whether the relative-path field ends up used for anything, now that districts were dropped —
  probably still worth keeping (future features, or just debugging), just not used to split a
  project into multiple cities.
- **Backend: Supabase (Postgres), not Firebase.** Chosen over Firebase specifically because
  "sum of lines of code per project, cumulative" is a `GROUP BY`/`SUM` query away in SQL, and a
  year-long project will likely want to query this data in shapes not anticipated yet (a
  history-over-time chart, say) — Postgres handles that more gracefully than a NoSQL aggregate.
  Considered and rejected: using a Claude-side Artifact's own database capability as the shared
  store — it isn't reachable as a plain HTTP API from an arbitrary local server, only from inside
  a published Artifact page or through Claude's own tool calls, so it can't be what many
  independent local `bot-crossing-hive` servers push to directly.
- **Sync cadence: slow poll, not live.** Each local server pushes/pulls on a cadence of minutes,
  not a live subscription — consistent with "cumulative, not live" above, and much simpler to get
  right than a real-time sync layer for a gain (instant cross-machine updates) that doesn't
  actually matter here.

**Backend superseded 2026-09-21: git-file storage, not Supabase.** Everything below describing
Supabase/Postgres/RLS/`hive-sync.mjs`/`design/supabase-schema.sql` is history, kept for the
reasoning trail, but no longer what's running — the user pivoted explicitly: "we share a github
repo, the github repo stores the agents and lines of code, and project context — that's the most
important part." The app now only ever reads/writes plain files in the repo's own working tree
(`.hive/agents/<device-id>.json`, one file per machine so nothing ever merge-conflicts) and
**never runs `git add`/`commit`/`push` itself** — committing/pushing the resulting files is the
user's own normal git workflow, by their explicit choice ("never auto-commit or push"). Real
current files: `server/lib/hive-git.mjs` (`deviceId`, `writeLocalAgents`, `readTeamAgents`,
`setNickname`, `projectPathsOf`, `syncLocalAgents`, `startHiveSync`) and
`server/lib/project-setup.mjs` (`ensureProjectSetup` — provisions `.agent-context.md` + a
project-level Stop hook + `.claude/settings.json` merge, idempotent, additive-only, no git
commands). `design/supabase-schema.sql`, `tools/fake-hive.mjs`, `.env.example`,
`server/lib/hive-sync.mjs` and its tests are all **deleted**. Real side effect worth knowing: the
dev server's sync loop writes `.hive/agents/<device-id>.json` into *every* real local project it
scans, not just Tower City's own repo — confirmed present (as untracked files) in this repo,
`firefly`, and `kalshi-trading` after a dev session. That's the feature working as designed, not a
bug — nothing commits them, they just sit there until the user chooses to `git add` and push.

Nicknames: `setNickname` persists a per-thread display name into that same per-device JSON file,
survives a resync (the file is read before being overwritten). Team visibility split: only *your
own* threads are actionable in the sidebar (renamable, openable) — a teammate's completed threads
still show up as astronauts walking the same deck (`thread.remote` on the merged list), but never
in the sidebar's thread list and never get the "find me" beacon highlight
(`TowerColony._buildBeacons`/`_updateBeacons` explicitly skips `agent.thread?.remote`).

**Now implemented (2026-09-21):**
- **Auth decided and built**: no separate auth layer — the Supabase project's own `anon` key IS
  the shared team secret (settles the "not yet decided" question below in favor of the option the
  design record already guessed would win). `design/supabase-schema.sql` is the one-time setup
  script: `hive_threads` table, RLS enabled, permissive `anon` insert/update/select policies, no
  delete policy (cumulative, deny-by-default). Not yet run against a real Supabase project —
  nobody has created one yet, this is prep for when someone does.
- **`server/lib/loc-counter.mjs`**: `transcriptLoc`/`countLinesOfCode`, mtime-cached, mirrors
  `transcriptSkillCounts`'s shape exactly. Sums `Write.input.content`, `Edit.input.new_string`,
  `MultiEdit.input.edits[].new_string` line counts — Claude Code transcript format only (same
  scope limitation as skill-usage counting; no Codex equivalent, for the same "format
  unconfirmed" reason noted below). Known accepted approximation per the design record above
  (double-counts edited-then-landed lines, still counts later-reverted ones). One test:
  `test/loc-counter.test.mjs`.
- **`server/lib/hive-sync.mjs`**: the push/pull client. `hiveConfigured()` gates everything on
  `HIVE_SUPABASE_URL`/`HIVE_SUPABASE_ANON_KEY` being set — unset, the server runs exactly as
  before (solo, no network calls, logs one line at startup saying so). `pushThreads` upserts
  every locally-completed thread (`hasTranscript && !hasLiveProcess`) via PostgREST
  `Prefer: resolution=merge-duplicates`; `pullCityTotals` fetches every row and sums
  `lines_of_code` per `project` client-side (no Postgres view/RPC — a `ponytail:`-style
  deliberate simplification, fine at small-team row counts, called out in-file as the upgrade
  path if it ever isn't). `project_path` is pushed as `thread.worktree` — never the absolute
  path, per the design record's own constraint. A per-machine `device_id` (random UUID) is
  generated once and cached at `~/.bot-crossing-hive/device-id`; never surfaced in any API
  response beyond the raw sync payload, and no UI reads it. `startHiveSync(scanThreads)` runs an
  immediate tick then polls every `HIVE_SYNC_INTERVAL_MS` (default 5 min) — wired into both
  `server/serve.mjs` (production) and `vite.config.js`'s dev-server plugin. `GET
  /api/hive/city-totals` (`server/api.mjs`) exposes the last-pulled cache; never blocks a request
  on the network itself.

  - **New, separate feature: `tower-city.html` + `src/towers/`** (`main.js`, `tower-mesh.js`).

  - **Growth model**: `LOC_PER_GROWTH_POINT` (100) lines earns one growth point; each point rolls
    `GROW_EXISTING_CHANCE` (0.8) to add a floor to a random not-yet-capped existing tower,
    otherwise (or if every tower is capped) spawns a new one with a fresh random `maxLevels`
    (2–8). A new tower's slot is a random *free* slot on the deck, not sequential — an earlier
    version always filled slot 0 (a cell's centre) first, which read as planned rather than grown.

    onto the side of some upper floors for an "accreted over time" look. Also
    `createWindmill(seed)` — same `windturbine_tall`/`_low` parts the original `antenna` building
    uses, but as two independent meshes (mast + rotor) instead of one merged buffer with the
    vertex-shader spin trick, since a plain `rotor.rotation.y += dt * speed` is plenty for a
    handful of decorative turbines on empty deck slots (~35% chance per empty slot).

    map, not `{solo: true}` — `solo` is only populated for nodes that are themselves a mesh (see
    `kit.js`'s `harvest`), and the fan node isn't one; using `solo` there throws on the very first
    windmill. The mast *does* need `solo: true` (matches the original `antenna` kind exactly).

    dropped 100 → 20 (a real multi-thousand-line project read as "too small"). Deck footprint was
    also decoupled from tower count — it used to only grow when a new tower happened to spawn,
    and `GROW_EXISTING_CHANCE` biasing toward height over new towers made that rare, so a big
    project's *ground* stayed tiny even with tall towers on it. Fixed by tracking cumulative
    growth points directly (`POINTS_PER_SLOT = 5`) and sizing the deck off that regardless of

    spawn directly on top of a windmill; now excludes both, and windmills re-sync after every
    growth batch, not just when a brand new tower happens to spawn.

    - **`src/towers/tower-colony.js`** — `TowerColony`, a `Colony`-shaped class (same

    - **Shipped untested, then actually tested — four real bugs found and fixed.** The
      Claude-in-Chrome browser tool would not hold a connection all session (connects, then
      drops before the next call, repeatedly), so every fix below came from the user pasting a
      screenshot of their own DevTools console, not from seeing it directly.
      1. **Slot-capacity crash.** `_spawnTower`'s "pick a random free slot" only excluded
         *tower*-occupied slots from capacity sizing, not windmill-occupied ones — once
         windmills had claimed part of the deck, `free` could be empty even though
         `plot.slots.length > towers.length`, handing `Plot.worldSlot` an `undefined` index and
         throwing `Cannot read properties of undefined (reading 'x')`. Fixed by sizing capacity
         off `towers.length + windmills.size + 1`, plus a fallback that grows the deck once more
         rather than crashing if it's ever wrong again.
      2. **The engine's frame loop has no error handling at all** (`Engine._loop` in
         `core/engine.js`: `for (const u of this.updaters) u.update?.(dt, this.elapsed)`, no
         try/catch) — an uncaught throw anywhere in a per-frame update doesn't skip a frame, it
         kills `requestAnimationFrame` for good, since nothing schedules the next one. That is
         what bug #1 actually looked like on screen: "a few astronauts walk in, then black,
         forever" — not an error dialog, because there isn't one. This is true of the *original*
         map too, not just this new view; worth remembering if the real colony ever silently
         freezes. Fixed here (not in `engine.js`, which stays untouched) by wrapping the whole
         `engine.add({update(){...}})` body in `app.js`, and every subsystem call inside
         `TowerColony.update` (astronauts/indicators/fauna/sky), in its own try/catch — doesn't
         fix a bug by itself, but turns "silently frozen forever" into "one broken subsystem
         skips a frame, logged, everything else keeps going."

         `AmbientLight`+`DirectionalLight` instead of reusing `world/sky.js`'s `Sky` class. Every
         KayKit part uses a real PBR material (roughness/metalness) — without a prefiltered
         environment map for it to reflect, those materials render close to black regardless of
         direct light intensity. Astronauts use a different, non-PBR material, which is why they
         stayed visible while the whole deck looked black. Fixed by swapping in the real `Sky`
         (same class the original colony uses), including its per-frame `update()`/`setFocus()`.
      4. **Settings changes never reached the colony at all.** `app.js`'s `settings.onChange`
         handler didn't call `colony.onSettingsChanged(...)` anywhere, and `TowerColony`'s own
         version of it was an empty stub — so the time-of-day slider (and `L` key) changed the
         *setting* but the sky never heard about it. Also fixed the "sky"-shaped planet's
         floating-island ground: it only renders where `mesh.userData.setFootprint(...)` has
         told its shader to, keyed to world-space cell centres — never called, so it showed
         nothing (or a stale shape) regardless of how many hex tiles the deck actually had. Both
         wired: `onSettingsChanged` forwards to `sky`/`astronauts`/`fauna` like the original does.
      5. **The "sky" island was still "messed up"** even after fix #4 — because #4 only clipped
         the *ground shader*, not the actual floating-island underside (rock/soil/vines hanging
         off the rim) or the scatter (trees/rocks), which is a *separate* system entirely
         (`Colony._buildIsland`/`_syncIslandRock`, `createSkyIsland` + `createHexIsland` in
         `world/skyisland.js`/`hexisland.js`). Built the real thing now: `_buildIsland()` (once
         per planet change) and `_syncIslandRock(st)` (cheap, called on every deck-capacity
         change/project switch — renamed from an earlier, incomplete `_syncIslandFootprint`) both
         exist in `tower-colony.js`, plus `onIsland(x,z)` so `createScatter`'s `inside` filter
         keeps trees off the ground that's been clipped away. **Real null-crash found in this
         path**: `_buildIsland()` calls `_footprintRadius(this.current)`, and `this.current` is
         still `null` at boot (`applyPlanet()` runs before any project is ever selected) — if the
         restored planet was "sky" (Aerie), this threw immediately, before `poll()` ever ran,
         leaving "Scanning for agent threads…" up forever with **no console output at all**
         (`boot()` is fire-and-forget with no `.catch`, so the rejection just vanished). Fixed the
         null case in `_footprintCells`, and separately hardened `boot()` itself so this whole
         *class* of bug can't recur: `applyPlanet()` and `poll()` are both wrapped so the boot
         screen is guaranteed to come down (with a toast naming the error) no matter what throws.
      6. **Agent placement**: originally a point on a *circle* around the deck's centre, which
         can land in the gap between two non-adjacent hex cells (the footprint is a cluster of
         tiles, not a filled disc) — "some of them aren't on the hex". Fixed by picking an actual
         cell from `st.plot.localCenters` first, then jittering only within a safe radius inside
         it. Also added real movement: the chosen cell/jitter reseeds every `WANDER_PERIOD_MS`
         (25s) instead of once forever per thread, so the crew visibly wanders the deck over time.
      7. **Highlight redesigned twice**: a flat ground ring (v1) got lost behind towers from
         above — fixed with `depthTest: false` so it draws through geometry, but a *flat, on-the-
         ground* ring was still the wrong shape to "outline the agent itself, not a circle under
         it". Replaced with a ring at chest height, billboarded to the camera's own quaternion
         every frame (`this.camera.quaternion`) so it always presents as a full halo around the
         character from any angle, instead of a decal only visible edge-on from this game's own
         low camera angle.

# Bot Crossing — working notes

Fork of the upstream repo, running locally on Windows. Diverges from upstream in a few places
that aren't in any PR yet:

- **Windows terminal-opening support** (`server/lib/win.mjs`, new file): the `claude://` /
  `codex://` deep links have no real handler on this machine (a broken/stale registry entry for
  `claude://`, nothing at all for `codex://`), so `openThread`/`newSession` fall back to a real
  terminal command. Tries Wave Terminal (`wsh run`) first, then Windows Terminal, then a bare
  console window. Already-open threads get focused (`wsh focusblock`) via a block tagged with
  `bot-crossing:thread=<id>` in `setmeta`, instead of duplicating.

  **`wsh` needs env vars this server can't get on its own, and one real bug this repo had.**
  Bot-crossing's server is an external process from Wave Terminal's point of view — not a block
  it spawned itself — so unlike an interactive Wave terminal, it never gets these injected:
  - `WAVETERM_JWT` — every `wsh` command but the hidden `token` one refuses to run without it.
    Get a fresh one from any real Wave Terminal block: `echo $env:WAVETERM_JWT` (PowerShell) /
    `echo $WAVETERM_JWT` (bash). Long-lived (the current one expires 2027) — it does **not**
    need to come from the *same* block that's still open, a signed bearer token from any block
    works. Baked into the Startup-folder launcher (`bot-crossing.vbs`) — see its own comments if
    this ever needs redoing.
  - `WAVETERM_TABID` — `wsh run` needs this to know which tab a new block belongs in; without it,
    block *creation* fails outright (`blocks list`/`focusblock` still work with just the JWT,
    which is a misleading half-working state — it looks like dedup works because nothing new
    ever gets created to prove otherwise). Same source: `echo $env:WAVETERM_TABID`. Also baked
    into the launcher.
  - **The actual code bug**, independent of either env var: `wsh -b <id>` needs a full ORef
    (`block:<uuid>`), not the bare id `wsh blocks list` hands back in its JSON. A bare id is only
    resolved via a `WAVETERM_BLOCKID`-relative RPC lookup that nothing here has any reason to
    set, so `focusblock`/`setmeta` failed with `no WAVETERM_BLOCKID env var set` even with a
    valid JWT+TABID — silently, since the failure was caught and swallowed, so blocks kept
    getting created untagged, which meant dedup could never find them next time either. Fixed in
    `win.mjs` by prefixing every `-b` argument with `block:`. Traced by reading
    `resolveSimpleId`/`isFullORef` in `wavetermdev/waveterm`'s own `cmd/wsh/cmd/wshcmd-root.go` —
    if `wsh` ever mysteriously stops tagging/focusing again, that source is the place to recheck
    first, not the JWT/TABID (which have their own distinct, differently-worded error messages).
- **Exact Wave Terminal placement** — the web view block gets its own column, new terminal
  blocks fill columns capped at 2 stacked each. Stock `wsh run` has no placement flags even
  though the RPC (`CommandCreateBlockData.TargetBlockId`/`TargetAction`) supports it, so
  `tools/bin/wsh-patched.exe` is a locally-built `wsh` with `--target`/`--split` added — see
  `tools/README.md` to rebuild it (gitignored, not checked in) and `tools/wsh-run-target-split.patch`
  for the actual diff. `win.mjs` falls back to plain `wsh.exe` on PATH if the patched copy is
  missing. New columns must always anchor-split off the web block specifically, never off a
  previous column's own blocks — Wave's tree algorithm only inserts a sibling when the target's
  *parent* is already a row, and a 2-stacked column's blocks are children of a column-group node
  instead, so splitting relative to them nests inside that group rather than beside it.
